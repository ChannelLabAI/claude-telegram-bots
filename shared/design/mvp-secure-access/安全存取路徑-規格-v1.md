> 規格來源：觀星者　|　2026-09-01　|　起因：小米要求「參考 Zeabur 事故後，打造相對安全的存取路徑與對應 UI」
> 視覺稿：見同目錄 `安全存取路徑-UI-v1.html`
> 本檔為建單／開發／審查正本（可 diff）。**auth／安全變更必須走 FATQ → builder → bella → host-apply，設計者不自行部署。**
> 相關：本規格吸收並取代先前「身分可辨識 AC」的散點，統一成一條存取路徑。

## 0. 目標（一句話）

把 MVP 的存取從「共用密碼為主、身分不透明」升級為「**各自 Google 身分為主、共用密碼降為標示清楚的 Demo 次路徑**」，並讓使用者在每一頁都**看得出自己是誰、是哪種存取層級**。

## 1. 設計原則（對應 Zeabur 事故教訓）

| 原則 | 白話 | 對應教訓 |
|---|---|---|
| 最小權限 | 預設給最低權限，要更多得先驗證身分 | 過權憑證是 Zeabur 的死因 |
| 邊界切分 | demo／真實、member／admin、各人資料，彼此隔開 | 切好邊界才能限制波及範圍 |
| 身分透明 | 使用者永遠看得到「我是誰、我是哪一層」 | 共用身分不透明＝使用者被蒙在鼓裡 |
| 可歸屬 | 真實用途走個人身分，不用共享憑證 | 共享靜態憑證無法歸屬、無法個別撤銷 |
| 可偵測 | 存取／異常留痕、可告警 | 決定災情大小的是「多快偵測並切斷」 |

## 2. 存取路徑（使用者實際走的路）

```
訪客開啟網址
      │
      ▼
 ┌──────────────── 入口頁（重新設計，奶油裸粉品牌） ────────────────┐
 │  主路徑（突出）：使用 Google 帳號登入                             │
 │     ├─ 白名單內  → 進入，取得「本人身分」（資料隔離、可歸屬）     │
 │     └─ 不在白名單 → 顯示「向管理員申請存取」（不靜默拒絕）        │
 │                                                                  │
 │  次路徑（弱化、標清楚）：以訪客身分瀏覽 Demo（共用密碼）          │
 │     └─ 進入「共用檢視帳號」，唯讀 member，橫幅警告勿放真實資料    │
 └──────────────────────────────────────────────────────────────────┘
```

## 3. UI 規格（四個畫面／狀態）

### 3.1 入口頁（重設計）
- 品牌：奶油裸粉（取代現行深藍 gate 頁，統一品牌、也回應小米「深藍太科技」）。
- **主行動：「使用 Google 帳號登入」大按鈕**，副標「各自獨立帳號 · 你的內容只有你看得到」。
- 「或」分隔線後，**次行動弱化**：「以訪客身分看 Demo」小按鈕，緊鄰**警告晶片**：「共用示範環境 · 請勿放入真實或敏感資料」。
- 頁尾：「看不到你的帳號？→ 向管理員申請存取」。
- ⚠️ 不得洩漏兩層密碼機制（延續 a9d3；入口頁只呈現「訪客 Demo」單一次路徑，admin 密碼層不出現在 UI）。

### 3.2 身分列 · 狀態 A：Google 本人
- 右上：真實姓名首字頭像 + 全名，旁附 `🔒 僅你可見`，及「登出」。
- 「我的內容」只顯示自己的（見 §4）。

### 3.3 身分列 · 狀態 B：共用訪客（Demo）
- 右上：中性頭像（如「共」）+ 標籤 **「共用檢視帳號 · Demo」**（**不顯示任何人名**）。
- 黃色提示條：「此為共用示範身分，內容與其他訪客共用；要私有內容請切換為本人。」
- 明確入口按鈕：**「切換為我的帳號 →」**（走 Google 登入）＝招募路徑，使用者自助升級，我方不需逐人判斷。

### 3.4 申請存取（非白名單 Google 使用者）
- 卡片：「此信箱（顯示該 email）尚未獲授權。」
- 「已記錄你的申請，管理員核准後即可用自己的帳號登入。」
- **實作僅記錄／通知管理員，不自動加白名單**（加白名單＝授權變更＝老兔決定，見 §6）。
- ⚠️ **永不加入自動核准或條件式放行**（anya 複審點名：此新入站通道的安全性在於「它不會自動放行」，後續版本不得為了「順暢」破壞這條）。

### 3.5 列舉安全（enumeration safety，回應 anya 複審提問）
> anya 複審提問：申請存取的回應會不會洩漏「某信箱在不在白名單」？若名單內／外行為不同（訊息、延遲、寄不寄信），就是成員列舉通道。**原 v1 未明確處理，v1.1 補上如下。**
- **結構性緩解（本設計天生具備）**：「申請存取」只在**完成 Google OAuth 之後**出現 —— 使用者已證明擁有該信箱。因此使用者只能得知**自己能驗證的帳號**是否在白名單，**無法拿任意他人信箱當預言機（oracle）逐一探測**。這不是一個開放的「輸入任意 email 查詢」入口。
- **入口頁「向管理員申請存取」連結不得做成「自由輸入任意 email 的表單」**：一律先走 OAuth 再申請，維持上述前提。
- **若未來確有需要接受手動輸入 email**：回應必須**對白名單內／外一致**（相同訊息、相同延遲、不因是否在名單而寄／不寄不同的信），且通知只發給**管理員**、不對申請者透露名單狀態差異。
- ⚠️ **時序／寄信等實作層 side-channel 由獨立安全複審驗證**；本節定的是「行為契約」，實作是否真的等時、真的不洩漏差異，屬複審範圍。

## 4. 資料隔離（硬性 AC）
- 未來「我的內容」列表端點**必須 `WHERE user_id = session user.id`** —— 趁尚未建置先釘死，杜絕日後引入洩漏。
- 共用訪客看到的是「共用池」內容且介面明確標示為共用。
- 現況已驗：寫入綁 `user.id`、produce 讀 proposal 為 `id=? AND user_id=?`（mvp-server.ts:349/377）。

## 5. 工程硬化項（標為實作細節，供 builder／安全複審評估）
1. **公開曝險**：cloudflared 公開通道嚴格 demo-only／時間盒；真內部用轉私有（IP allowlist／VPN）＝最大降面。
2. **共用密碼**：視同半公開，定期輪換、每輪 demo 後換。
3. **session 簽章密鑰**：目前存 app sqlite kv（mvp-server.ts:187-191）；評估移出或強化 DB 保護（DB 外洩＝可偽造任意 session）。
4. **偵測**：登入／存取異常告警（現僅稽核＋rate-limit，主動告警偏弱）。

## 6. 需老兔拍板（授權範圍，設計者與 anya 均不自行決定）
- **這頁未來是否支援多人各自登入**（決定 §3.1 主路徑與 §3.4 申請流程的 AC 範圍）——產品能力決策，非單次授權。
- 若支援：**開白名單給誰**由老兔核准，經他或 FATQ 過審方式加，不由任一 bot 直接改 env／systemd。
- 在他回覆前：白名單維持現狀；§3.4 只做「記錄＋通知」不自動放行。

## 7. 驗收準則（AC 草案；anya 建單時精修）
1. 入口頁呈現「Google 登入為主 + 訪客 Demo 為次且帶警告」兩條路徑，奶油裸粉品牌。
2. 登入後身分列正確區分並顯示兩種狀態（本人／共用訪客），共用訪客不顯示人名、且提供「切換為我的帳號」。
3. 非白名單 Google 使用者看到「申請存取」而非靜默拒絕或英文錯誤。
3b. 申請存取不得成為成員列舉通道：申請僅在 OAuth 後觸發、入口連結不接受自由輸入 email；若接受手動輸入則白名單內／外回應在可觀察維度上一致（時序 side-channel 由安全複審驗證，見 §3.5）。
4. 「我的內容」列表（若建置）只回傳登入者自己的資料。
5. 全程無英文技術錯誤碼；文案為中文人話（延續 329f 教訓）。
6. **live_verify 必須能失敗**：以兩個不同帳號登入，驗證身分列顯示不同且不再都顯示「米」；以未授權 email 驗證走到「申請存取」而非放行。
